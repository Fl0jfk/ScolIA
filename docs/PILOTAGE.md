# Pilotage du chantier ScolIA (sessions IA)

Ce document est la **mémoire du pilotage** : comment le travail est organisé entre sessions, ce qui a été appris, et où en est la file. Il est écrit pour que n'importe quel pilote — la session actuelle, une session suivante, ou un modèle plus récent — puisse reprendre le chantier sans rien perdre. À relire en premier, avec `CLAUDE.md`, `docs/DECISIONS.md`, `docs/SOCLES.md` et `docs/ROADMAP.md`.

## 1. Rôles

| Rôle | Modèle | Ce qu'il fait | Ce qu'il ne fait pas |
|---|---|---|---|
| **Pilote** | Opus | Décide de l'ordre, rédige les consignes, tient ce document, parle à Florian, pousse sur `ENT` après contrôle. | Ne code pas les lots ; ne pousse jamais sans validation verte. |
| **Contradicteur** | Opus (sous-agent ou session courte) | Relit **avant lancement** chaque vague de consignes et chaque décision structurante : décisions de Florian bien incluses, modèle juste, plages de migration, dépendances entre branches, risques de conflit, oublis. Relit aussi ce document à chaque jalon. | Ne décide pas ; rend une liste d'objections que le pilote traite ou écarte par écrit. |
| **Concepteur de socle** | Opus | Conception de fond d'un socle (`docs/socles/NN_*.md`). | Pas de code. |
| **Personas (conception)** | Opus | Passe de personas sur une conception : manques, réglages en trop signalés. | Ne supprime rien. |
| **Équipe de code** | Sonnet (sous-agents Sonnet, recherches Haiku) | Un lot par session, sur sa branche, tests et revue de sécurité. | Ne pousse jamais sur `ENT`, `main`, `dev`. |
| **Intégrateur** | Sonnet, **un seul à la fois** | Prend la file d'intégration dans l'ordre, fusionne, fait valider par la **CI GitHub** (workflow `ent-rust.yml` lancé à la main sur la branche d'intégration), corrige ce que la fusion casse. | N'ajoute pas de fonctionnalité. |
| **Recette par personas (logiciel)** | Opus + sous-agents Sonnet | Après le code d'un socle : personas qui travaillent et **attaquent** le logiciel réel (données de labo), chaque trouvaille devient un test. | Pas de données réelles. |

## 2. Règles apprises (à appliquer sans exception)

1. **Toute consigne métier va dans le message de lancement d'une session**, jamais dans un message envoyé ensuite : une session refuse, à raison, d'agir sur la demande d'une autre session (F-012). Pour changer une consigne en cours de route : nouvelle session dédiée qui part de la branche.
2. **Choisir le modèle à chaque lancement** (F-010) : Sonnet par défaut, Opus pour conception, personas, contradicteur, recette.
3. **Plage de migrations réservée avant lancement** dans `docs/socles/MIGRATIONS.md`.
4. **La CI GitHub fait foi** pour valider une intégration : les conteneurs cloud redémarrent et coupent les suites longues (F-012). Les suites locales servent au développement, découpées par paquet pour être reprises.
   **Le job « Backend » est parallèle depuis `ent-ci-parallele` (2026-11-09)** : le job unique de 1 h 45 à 3 h 50 (suite complète d'un bloc, un seul fil, une seule base ; run séquentiel 42569240935 = **3 h 51**) est remplacé par `backend-lint` (clippy avec et sans labo, `ent-types -D warnings`, compilation de production, séparation L4), `backend-archive` (compile une fois les binaires de test, avec et sans labo, en archives `cargo nextest archive`), `tests-labo` (**20 tranches** `count:i/20`, un fil chacune, **un PostgreSQL éphémère par tranche**), `tests-sans-labo`, puis le job final `Backend (clippy, compilation, tests)` (nom conservé) qui exige tous les jobs verts **et** vérifie la couverture. Un nouveau test est réparti automatiquement (partition par rang, pas de liste de modules à tenir à jour). `cargo-nextest` est épinglé (0.9.150, installé par `taiki-e/install-action`, déjà utilisé pour `cargo-deny`). **Contrôle de couverture** : l'inventaire `cargo nextest list` de chaque archive est comparé aux journaux des tranches ; tout test listé non exécuté, exécuté deux fois ou exécuté sans être listé fait échouer le job final, et le tableau par binaire est écrit dans le résumé du run. Les tests de documentation (`cargo test --doc`) restent exécutés par `backend-archive` (nextest ne les couvre pas). Lire le journal du job final avant de chercher dans les 20 tranches : il nomme les tests en échec.
5. **Une seule file d'intégration**, dans l'ordre ; pas deux intégrations en parallèle sur des bases différentes.
6. **Rien sur `ENT` sans les quatre jobs CI verts** (formatage, audits, backend, frontend) et un contrôle du pilote (journal des commits, `MIGRATION_TAG`, aucun test ignoré ajouté, décisions de Florian respectées).
7. **Trois sessions actives en continu** (Florian, 2026-11-08) ; on peut en lancer une ou deux de plus quand les autres ne font qu'attendre un retour de CI ou de tests. On accélère en fin de semaine si le quota hebdomadaire reste large. Jamais plus de 6 à 7 : au-delà, la limite d'usage coupe tout.
12. **Recommandations appliquées par défaut** (D-031) : on tranche selon la recommandation écrite, sauf engagement extérieur, interdiction ou contradiction ; le point quotidien les liste.
11. **Toujours répondre à Florian en français** (Florian, 2026-11-09), y compris les points d'étape, les rapports techniques et les résumés de sessions ; termes techniques expliqués simplement.
10. **Suivi toutes les 30 minutes** (rappel programmé) : voir ce que font les sessions, relancer la CI, archiver, remplacer une session finie ; ne jamais laisser les sessions sans travail.
8. **Archiver une session** dès que son travail est poussé et qu'elle n'attend plus rien.
9. **Tout ce qui compte s'écrit dans le dépôt** (décisions, état, leçons), jamais seulement dans une conversation.

13. **Exigences E1–E14 (PRA, D-038 proposé, `PRA_SAUVEGARDES.md` §18.4)** : rappelées dans chaque lancement de session de code et vérifiées à la revue du pilote avant push sur ENT (etablissement_id, références composites, UUID, pas de BYTEA, horodatages, journal, migrations rejouables, files neutralisables à la restauration, pas de JSON-mémoire, clés inventoriées, registre des tables, RLS, pas de donnée d'établissement dans les journaux techniques).
14. **Défauts Next.js corrigés en Rust (D-051)** : tout lot qui porte un module Next.js liste les défauts NJ-xx de `ALERTES_NEXTJS_PROD.md` qu'il ferme, avec un test de non-régression par défaut ; aucun contournement d'authentification du Next.js n'est repris (les actions passent par le compte connecté). Vérifié par le pilote avant push sur ENT.
15. **Migrations versées sur ENT : on ne les modifie plus** (2026-11-11). Toléré une dernière fois pour 561 (D-036 lot 2) car aucune base ScolIA n'est déployée ; à partir de la répétition de Noël (D-057), toute correction passe par une nouvelle migration, sinon la vérification d'empreinte de sqlx casse les bases déjà migrées.
16. **Ne pas gaspiller la CI** (2026-11-11) : un nouveau lancement sur une branche annule le passage en cours (souvent après 30–60 min d'attente). On lance la CI seulement quand le lot est fini et que les tests locaux ciblés sont verts ; on ne relance pas pour un commit de documentation ou de rapport (il part avec le commit suivant, ou le pilote le reprend) ; on regroupe les corrections avant de relancer ; si un passage échoue sur une tranche, on corrige tout ce qu'on peut en local avant de relancer.
17. **Fusion pilote sans relancer la CI** (2026-11-11) : quand un lot est vert sur sa branche mais qu'ENT a avancé entre-temps, le pilote peut fusionner ENT dans ce lot et verser le résultat **sans nouveau passage de la branche**, à trois conditions : (a) les fichiers touchés des deux côtés ne se recouvrent que dans des zones disjointes (ajouts séparés, documentation) ; (b) aucune migration de l'autre côté ou MIGRATION_TAG cohérent ; (c) `cargo check` des crates touchées passe en local. Le passage déclenché par le push sur ENT fait alors foi ; s'il est rouge, correction immédiate en priorité absolue.
18. **Audit Fable après chaque gros bloc** (D-060) : quand un bloc fonctionnel complet arrive sur ENT, le pilote lance un audit Fable en lecture seule sur ce bloc (`docs/audits/AUDIT_FABLE_<n>.md`), de préférence juste après une remise à zéro des quotas, puis répartit les correctifs en sessions de code (plages de migrations dédiées). Prochain : messagerie + emploi du temps dès qu'ils sont sur ENT.
19. **Retour à 3 sessions au maximum** (Florian, 2026-11-11 au soir) : la poussée du 11 novembre (jusqu'à 16 sessions) se termine ; on ne relance **aucune nouvelle session** tant que les sessions en cours ne sont pas finies, puis on travaille avec **3 sessions simultanées au plus** (pilote non compris), code et conception confondus. Les sessions arrêtées par le quota sont seulement relancées, pas remplacées. Une nouvelle poussée se décide avec Florian (remise à zéro des quotas).
20. **Quota : 3 sessions actives au plus, aucune session Fable** (Florian, 2026-11-12). L'audit Fable n° 2 a vidé la limite des 5 heures en une dizaine de minutes : plus de session Fable sans accord explicite de Florian (D-060 suspendue). **Mise à jour (Florian, 12-11 après-midi)** : toutes les sessions non-Fable sont relancées ensemble (seules les sessions Fable consommaient le quota de façon massive) ; les sessions Fable restent arrêtées, à reprendre éventuellement en fin de file. Les autres sessions restaient en pause (interrompues) et passaient par vagues de 3, par ordre de priorité du plan de bascule ; une session terminée est remplacée par la suivante de la file. Consigne aux sessions : pas de sous-agents, lectures ciblées, tests locaux limités au périmètre touché. **Mise à jour (Florian, 14-11, 6 h 45)** : jusqu'à **6 sessions** simultanées (quota hebdomadaire à 64 %, remise à zéro le 15-11 à 10 h) ; toujours aucune session Fable sans accord.
21. **Droits par défaut : une fonction par socle** (Florian, 2026-11-13). Deux fusions de suite ont cassé `modele_par_defaut` (`ent-auth/src/actions.rs`) : git entrelaçait les blocs de deux socles ajoutés au même endroit, sans signaler de conflit. Les modèles des socles récents sont désormais chacun dans leur fonction (`socle_NN_<domaine>(role, &mut d)`), placées après `modele_par_defaut`, qui ne fait que les appeler dans l'ordre. **Un nouveau lot ne modifie jamais le bloc d'un autre socle** : il ajoute sa fonction (ou complète la sienne) et **une seule ligne** d'appel. Toute modification de ces fonctions est vérifiée par comparaison de la sortie de `modele_par_defaut` pour les 12 rôles avant et après (aucun changement attendu hors des droits du lot).
22. **Vérifications locales du pilote : un répertoire de compilation partagé ment** (2026-11-13). Quand plusieurs copies de travail partagent un même `CARGO_TARGET_DIR`, cargo peut réutiliser une crate compilée depuis une autre copie (même nom de paquet, fichiers plus anciens) : faux « identique », ou erreur de compilation fantôme. Règle : avant de vérifier une copie déjà compilée ailleurs, `touch` de ses sources (`find crates -name '*.rs' -exec touch {} +`, idem migrations) ; pour une comparaison entre versions (droits, sorties), un répertoire de compilation distinct par version. Les copies fraîches (nouveau worktree) ne sont pas concernées.
23. **Dépendances (D-062)** : aucune nouvelle dépendance sans justification écrite « ne peut pas être codée à la main » ; la cryptographie n'est jamais codée à la main (briques déjà présentes en priorité). Toute dépendance nouvelle est présentée à Florian avant ajout.
24. **Enchaînement des lots (Florian, 2026-11-14)** : une session ne reste jamais à l'arrêt en attendant sa CI. Dès que la CI du lot N est lancée, elle commence le lot N+1 de son socle sur une **nouvelle branche créée depuis la tête du lot N** (`…-code-N+1`). Quand la CI du lot N rend son verdict : vert → elle envoie le SHA vert au pilote et continue ; rouge → elle corrige sur la branche du lot N, relance UNE CI, puis rebase la branche N+1 sur la correction. Le pilote verse les lots dans l'ordre. **La règle 1 reste entière** (essai du 14-11 : les sessions refusent, à raison, une mission reçue d'une session pair) : l'enchaînement est donc écrit **dans le message de lancement**, sous forme d'une suite de 2 ou 3 lots du même socle, avec la méthode ci-dessus. Une session qui a fini sa suite est archivée et remplacée par une session neuve portant la suite suivante. Les règles 14 et 21 à 23 s'appliquent à chaque lot.
25. **Base des branches de code** (2026-11-14) : une branche de code part **toujours d'`origin/ENT`**, jamais d'`ent-mc0hoe` (documentation de pilotage). Les consignes de lancement le disent explicitement (les conceptions se lisent par `git show origin/ent-mc0hoe:…`, sans changer de branche). Contrôle du pilote avant tout versement : `git log --oneline <lot> --not origin/ENT` ne contient que les commits du lot, et aucun ne touche `docs/POINT_QUOTIDIEN.md` ni `docs/PILOTAGE.md`. Incident du 14-11 : N0a et N0b du socle 8 étaient partis d'`ent-mc0hoe` (232 commits de pilotage) ; N0a rejoué par `cherry-pick` sur ENT et recontrôlé par une CI.

**File d'attente (12-11)** : actives = emploi du temps T0–T2 (10), internat I0–I1 (41), correctifs audit « données sensibles ». En pause, dans l'ordre : voyages V0c, absences du personnel A0–A1 (15), agenda AG0–AG1 (19), correctif SSO S-01/B-02, correctifs audit « infrastructure », registre des migrations (D-036), stages ST0–ST1 (39), cahier de textes (20), assiduité AS1–AS2 (12), portail P2–P3 (29) ; puis conception N1 « Demandes » (Opus).

## 3. Cycle d'un socle (D-021)
Conception (Opus) → personas sur la conception (Opus) → lots de code (Sonnet) → intégration (file) → recette par personas sur le logiciel (Opus) → relecture de Florian. Un socle n'est « fini » qu'après la recette.

## 5. Transmission à un futur pilote
Un pilote qui reprend : lire ce document, `CLAUDE.md`, `docs/DECISIONS.md` (les décisions de Florian font foi), `docs/ROADMAP.md` (jalons de preuve), `docs/SOCLES.md` (carte), `docs/socles/` (conceptions), `docs/PROJECT_STATUS.md` (état technique), `docs/DECISIONS_AND_FAILURES.md` (erreurs à ne pas refaire) ; lister les sessions et les branches ; reprendre la file du §4. Les conceptions et les décisions sont indépendantes du modèle : un modèle plus récent peut les approfondir sans les refaire.
