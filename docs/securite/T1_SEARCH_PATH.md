# T1 — « Une table temporaire ne trompe aucune fonction de la base » (livraison)

Chantier transverse de sécurité, branche `ent-transverse-t1-search-path` (base `origin/ENT` a39f0892), migration **690**.
Statut : **implémenté et testé en local** (base neuve, modes permissif et strict, rejeu) ; CI : voir §9. Non « prêt production » : le `REVOKE TEMP` (§7) est un ordre de propriétaire à exécuter base par base.

## 1. Constat, corrigé et confirmé par le catalogue

- PostgreSQL cherche les relations dans `pg_temp` **en premier**, même quand `pg_temp` n'est pas dans le `search_path` ; `TEMP` est accordé à PUBLIC par défaut. Une session du rôle applicatif pouvait donc désarmer une garde dans sa session : `CREATE TEMP TABLE ent_xxx (LIKE public.ent_xxx)`.
- Pas d'escalade pour les fonctions « invoker » (aucune n'est `SECURITY DEFINER`, parmi les 487 fonctions inventoriées). **Constat en plus, non prévu par la consigne** : 3 fonctions `SECURITY DEFINER` (`ent_fin_purger_etablissement`, `eva_reprendre_existant`, `eva_reprendre_tout`) portaient `search_path = pg_catalog, public` **sans `pg_temp`** : `pg_temp` restait cherché en premier, avec les droits du propriétaire. Là, la table temporaire pouvait détourner une fonction qui s'exécute avec des droits supérieurs : la garde de 690 les corrige (`… , public, pg_temp`) et exige désormais `pg_temp` **en dernier** partout.
- La migration 2407 avait déjà traité 13 fonctions du cahier (et un test de `tests_cahier.rs`) ; 690 généralise.

## 2. Inventaire (base neuve, migrée jusqu'au bout, avant 690)

Requête : fonctions de `public` (`pg_proc` joint à `pg_namespace`), hors fonctions d'extension (`pg_depend`, `deptype = 'e'`), `prokind` `f` ou `p`, sans `search_path` dans `proconfig`.

| Total | Langage | `SECURITY DEFINER` | Dans une politique RLS | Dans un index / contrainte / colonne générée | Déclencheur |
|---|---|---|---|---|---|
| **487** (+ 28 déjà conformes ou à corriger : 21 `pg_catalog, public, pg_temp`, 4 `pg_catalog, pg_temp`, 3 `pg_catalog, public` à corriger) | 364 `plpgsql`, 123 `sql`, 0 autre | **0** (les 4 `SECURITY DEFINER` du schéma portaient déjà une clause, dont 3 incomplètes) | 2 : `ent_rls_etablissement`, `ent_rls_strict` (844 tables, 1 688 dépendances) | 3 : `ent_coord_groupe` (index), `ent_inscription_etat_valide` et `ent_siret_cle_valide` (contraintes CHECK) ; aucune colonne générée ni valeur par défaut | 294 fonctions servent de déclencheur |

Les 123 fonctions `sql` se répartissent ainsi (analyse du corps : une relation de `public` est-elle citée ?) : **29** sans aucune relation (« pures »), **25** retournent un ensemble, lisent des tables et sont **inlinées** (une 26e, `ent_eleves_lecture_seule`, retourne un ensemble mais ne cite aucune relation : rangée parmi les pures) par le planificateur (vérifié : `EXPLAIN` sans « Function Scan »), **69** scalaires qui lisent des tables (jamais inlinées : une sous-requête empêche l'inlining ; `SET` ne leur coûte que la sauvegarde du réglage). ## 3. Migration 690 et exclusions justifiées

`ALTER FUNCTION … SET search_path = pg_catalog, public, pg_temp` sur toutes les fonctions de l'inventaire, **sauf** :

**a. 29 fonctions « pures »** (`PURES`, `garde_search_path.rs` : une justification par fonction) — corps sans aucune relation de `public` (réglages de session, calendrier, normalisation de texte, contrôles de format, ou simples appels de fonctions qui portent leur propre clause). Rien à détourner ; `SET` ferait perdre l'inlining dans les politiques RLS (`ent_rls_etablissement`, `ent_rls_strict`), les contraintes et les index. Le test **vérifie** à chaque exécution que leur corps ne cite aucune relation : si un lot en ajoute une, il échoue.

**b. 25 fonctions `LANGUAGE sql` retournant un ensemble et inlinées** (`QUALIFIEES`) — messagerie (`ent_msg_fil_lisible`, `ent_msg_boite_membres`, `ent_msg_mes_participations`), cours du jour (`ent_public_cours_jour`, 26 fichiers), attendu de l'internat, évaluations, élève… Leur corps est **recréé dans 690 avec toutes les relations qualifiées `public.`** ; le code qui fait ce travail lit la définition **en vigueur dans le catalogue** à l'exécution (aucune copie de définition dans le fichier : un lot qui a redéfini la fonction avant 690 n'est pas écrasé) et rend un texte identique quand il est rejoué. Sûr parce que : (1) seules les relations étaient exposées (`pg_temp` n'est jamais cherché pour les fonctions ni les opérateurs) ; (2) le test crée, pour **chaque** relation citée par chaque fonction, une table temporaire homonyme et vérifie que le plan `EXPLAIN (VERBOSE)` n'en lit aucune, **et** que la fonction reste inlinée ; (3) un **témoin** (une fonction non qualifiée du même genre) prouve que la méthode voit bien le détournement ; (4) la différence avec l'ancienne définition est strictement l'ajout de `public.` (relue sur `ent_msg_fil_lisible`, plans identiques avant et après).

**Reste à faire : aucun** pour l'inventaire. Résiduels assumés : (i) les fonctions « pures » qui citent des **types** de relation (`ent_dem_fait`, `ent_import_ligne`, `ent_parametre`, `ent_eleve_enseignement` en paramètre) : le type est lié par identifiant à la création, une table temporaire de même nom ne peut qu'**échouer** un appel, jamais lui faire lire autre chose ; (ii) un `SET` de session `search_path` vers un schéma où le rôle a `CREATE` n'est pas traité ici (le rôle applicatif n'a `CREATE` nulle part : section 3 de `RLS_ISOLATION.md`).

## 4. Mesures

Base locale neuve (PostgreSQL 16, `fsync=off`), rôle applicatif non propriétaire, RLS stricte ; médianes de 15 exécutions, `EXPLAIN (ANALYZE, BUFFERS, SUMMARY)`, millisecondes. « Avant » = base sans 690 ; « après » = avec 690 (état final : exclusions + qualification).

**Lecture typique d'une table RLS de grande taille** (table de mesure jetable de 600 000 lignes sur 2 établissements, politique posée par `ent_rls_poser`, jamais versée) :

| Requête | Avant (plan / exécution) | Après (plan / exécution) | Buffers |
|---|---|---|---|
| Agrégat sur 60 000 lignes (Seq Scan + filtre RLS) | 0,571 / 17,071 | 0,580 / **16,932** | 5 507 hits, identique |
| Index + `ORDER BY … LIMIT 50` | 0,230 / 5,861 | 0,239 / **5,938** | 1 360 hits, identique |

La politique n'appelle que `ent_rls_etablissement` et `ent_rls_strict`, exclues : **aucun écart** (plan et tampons identiques).

**Lecture qui traverse une fonction `sql` inlinée** (`ent_msg_fil_lisible`, jeu du labo, 89 fils lisibles pour le compte le mieux doté) :

| Variante | Requête « fils lisibles, LIMIT 20 » | Requête « + filtre précis » |
|---|---|---|
| Avant (inlinée) | 11,585 / 1,386 | 4,490 / 0,637 |
| **Après 690 (corps qualifié, inlinée)** | **11,560 / 1,349** | **4,434 / 0,633** |
| *Alternative écartée : `SET` partout, sans exclusion* | 0,817 / 7,638 | 0,298 / 3,047 |

Sans la qualification, `SET` aurait fait passer l'exécution de 1,4 à 7,6 ms (le corps est replanifié à chaque appel, planification de requête préparée comprise) : c'est la raison de la famille (b). Aucun écart mesurable avec la qualification.

## 5. Garde statique et dynamique (`crates/ent-db/src/garde_search_path.rs`)

Interroge le catalogue d'une base migrée : **échoue** si une fonction de `public` n'a ni `search_path` (commençant par `pg_catalog`, finissant par `pg_temp`) ni place dans `PURES` / `QUALIFIEES` (fichier unique, justifiées). Le message dit quoi faire (écrire la clause dans le `CREATE OR REPLACE FUNCTION` de la migration du lot ; n'exclure que si le corps ne lit aucune relation). Les deux listes sont comparées à celles de 690 ; une entrée disparue du catalogue échoue. Les lots futurs sont ainsi obligés de suivre la règle, et un `CREATE OR REPLACE` ultérieur qui efface la clause est vu. La garde prend le verrou partagé des rejeux (`garde_rejeu_partagee`).

## 6. Tests

| Test | Ce qu'il prouve |
|---|---|
| `garde_search_path::la_garde_du_catalogue_sur_une_base_neuve_puis_apres_rejeu` | **Base NEUVE créée pour le test** (état d'une installation, indépendant des rejeux partiels des autres tests) : zéro fonction de `public` hors règle ; inventaire > 400 fonctions ; toute fonction sans clause est exclue (nommée, justifiée) ; les 25 fonctions qualifiées résistent à un masque total (plan sans `pg_temp`, toujours inlinées) et un **témoin** non qualifié est bien détourné ; puis **rejeu de toutes les migrations** (`rejouer_tout`, qui efface les clauses) : 690 rejouée en dernier remet tout en place, et la garde repasse. Enfin la garde **a des dents** : une fonction nouvelle sans clause, un `CREATE OR REPLACE` qui efface la clause d'une fonction existante, un `search_path` sans `pg_temp` en dernier sont vus, avec le nom de la fonction et la marche à suivre |
| `garde_search_path::les_listes_sont_celles_de_la_migration_690_et_justifiees` | les listes `PURES` / `QUALIFIEES` du test et de 690 sont identiques, triées, sans doublon, justifiées, disjointes |
| `tests_search_path_t1::t1_gel_du_cahier_…` | **gel du cahier** : une 2e clôture reste refusée (« journal de clôture : le cahier de cette année est déjà clôturé », 23514) malgré des tables temporaires `ent_cdt_cloture` (avec une réouverture de complaisance) et `ent_annee_scolaire` (non close) |
| `tests_search_path_t1::t1_messagerie_la_garde_d_annulation_…` | **garde d'annulation de la messagerie** : la suppression de versions d'un message remis reste refusée (« ent_msg_version : ajout seul (ni modification ni suppression) », 23514) malgré un `ent_msg` temporaire où le message est encore différé |
| `tests_search_path_t1::t1_internat_la_garde_d_une_sortie_de_groupe_…` | **garde de l'internat** : l'annulation d'une sortie dont un élève est parti reste refusée (« sortie de groupe : des élèves sont partis, l'annulation est refusée », 42501) malgré une table temporaire `ent_internat_sortie_groupe_participant` vide |

Pourquoi une base neuve pour la garde : de nombreux tests (une trentaine de fichiers) rejouent un fichier de migration isolé dans la base commune de la tranche, et chaque `CREATE OR REPLACE FUNCTION` efface la clause jusqu'au prochain passage de 690. Une garde lancée sur la base commune échouerait selon l'ordre d'exécution (constaté en local). Les trois preuves, elles, rejouent **690 seule** au début (`migrate::remettre_search_path`, sous les verrous des rejeux) : elles éprouvent le mécanisme, pas l'historique de la base commune.

Chaque preuve a trois temps, dans des transactions toujours annulées : (1) sans masque, le refus et son message exact ; (2) **sous le rôle applicatif de test** (`ent_suite_stricte`, non propriétaire, sans `BYPASSRLS`, `app.rls_strict = on`, **avec** le privilège TEMP vérifié) avec la table temporaire homonyme remplie de lignes qui feraient passer la garde, le **même** refus, mot pour mot ; (3) **témoin** : sous le propriétaire, la clause est retirée dans la transaction (état d'avant T1) — le même masque désarme alors la garde et l'écriture passe. Sans le témoin, une preuve verte ne prouverait rien.

## 7. Rejeu

`rejouer_tout` rejoue d'anciennes migrations, et chaque `CREATE OR REPLACE FUNCTION` efface `proconfig`. 690 est dans le tableau `MIGRATIONS`, donc rejouée **après** les autres : le rejeu passe, puis la garde du §5 (testé dans `la_garde_du_catalogue_sur_une_base_neuve_puis_apres_rejeu`). Condition pour les lots suivants : leurs propres `CREATE OR REPLACE` portent la clause (la garde l'exige) ; 690 n'a pas à rester la dernière du tableau pour que la base soit conforme à l'installation (les migrations d'un lot suivant sont écrites conformes), mais **tout rejeu de migration antérieure à 690 efface les clauses** tant que 690 n'est pas rejouée après : `rejouer_tout` la rejoue, l'installation ne la rejoue pas.

## 8. Provisionnement (`docs/RLS_ISOLATION.md` §3.1)

Ordre de propriétaire, hors migration : `REVOKE TEMP ON DATABASE <base> FROM PUBLIC;` puis vérification `has_database_privilege(<rôle applicatif>, <base>, 'TEMP')` = `f`, et un `CREATE TEMP TABLE` d'essai refusé. **Le code applicatif ne crée aucune table temporaire** (`git grep` hors tests : aucune ligne, hors un commentaire de 2407 ; aucune migration n'en crée). Tests qui en créent : `tests_cahier.rs`, `tests_inscriptions_i5_passe3.rs`, `tests_internat_i3.rs`, `garde_search_path.rs`, `tests_search_path_t1.rs` — ils tournent sous le rôle du harnais (propriétaire local / `ent_ci` en permissif, `ent_suite_stricte` en strict) ; les preuves de T1 utilisent explicitement `ent_suite_stricte`. La base de test **ne reçoit pas** le `REVOKE` (les preuves ont besoin de TEMP pour montrer que l'attaque échoue malgré lui).
