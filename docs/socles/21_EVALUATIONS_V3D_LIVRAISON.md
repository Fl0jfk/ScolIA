## 3. Test web non déterministe (item 7)
**Test :** `web/crates/ent-web-server/tests/evaluations.rs`, `periode_complete_avec_le_client_du_frontend` (« l'absent ne compte pas » : moyenne `None` au lieu de 14,5).
**Cause (défaut réel du code, pas du test seul).** La périodisation « historique » d'un établissement n'est **pas** protégée contre le chevauchement (la contrainte d'exclusion ne vise que les périodes `origine = 'service'`, migration 335) : les périodes de notes de l'ancien modèle y sont projetées en `ent_periode`. Le test crée la période de notes `W…` : sa projection recouvre `T1` dans la **même** périodisation (constaté en base : `T1` 1ᵉʳ sept → 20 déc et `W…` 16 nov → 11 déc). Deux fonctions devaient dire de quelle période relève un jour, et ne s'accordaient pas :
* `eva_periode_eleve_jour` (463), période d'un élève un jour donné : elle joignait **deux** périodes et ne départageait que l'affectation (`ORDER BY a.date_debut DESC LIMIT 1`) : selon le plan d'exécution, `T1` ou `W…` ;
* `ent_periode_de_note_pour_classe` (472), période de notes → période de la classe : plus grand recouvrement, puis la plus ancienne.
La grille ne retient, pour la moyenne d'un élève, que les résultats dont **la période de l'élève** est la période demandée : un résultat rangé tantôt dans `T1`, tantôt dans `W…` donnait une moyenne tantôt pleine, tantôt vide (« une fois sur plusieurs »). Et dès qu'une période de notes **dépasse d'un jour** la fin du trimestre (ce qui arrive **depuis le 21 novembre** pour les tests qui créent « aujourd'hui − 10 j → aujourd'hui + 30 j » : 21 nov + 30 j = 21 déc > 20 déc), elle recouvre davantage sa propre projection que `T1` : les deux fonctions divergeaient alors **à coup sûr**. **Cinq tests de `tests_evaluations*` échouaient ainsi de façon déterministe sur la base locale au 2026-11-21** (`coefficients_de_matiere_et_regles_de_calcul`, `e2e_v3b_…`, `periode_complete_de_la_grille_…`, `tests_evaluations_v0::les_lectures_historiques_…` et `…une_absence_n_est_jamais_un_zero…`, tous « moyenne `None` ») : **la CI d'ENT les verra rouges dès qu'une exécution tombe à partir de cette date si 476 n'est pas versée** (le pilote doit le savoir).
**Ce qui n'est pas la cause** (écarté par lecture et par essai) : classe cherchée par code (le test crée une classe au code unique, dans l'année courante) ; année « préparation » (la classe et la période sont de l'année courante) ; accumulation d'établissements (21 passages successifs sur la même base : aucun échec).
**Corrections.** (1) Migration **476** : règle commune et **totale** dans les deux fonctions : à recouvrement égal, la période la **plus précise** (la plus courte), puis la plus ancienne (début, fin, identifiant) ; aucune donnée sans recouvrement n'est touchée ; mêmes signatures et colonnes. (2) Test web : « la période du jour » est choisie par le même ordre, au lieu de « la première trouvée ». (3) Test de base `v3d_item7_…` : deux périodes de notes (l'une contenue dans `T1`, l'autre qui la dépasse), six plans d'exécution forcés (`enable_hashjoin`, `enable_nestloop`, `enable_mergejoin`, sans index, sans balayage séquentiel) : la période de l'élève est toujours celle de la période de notes, jamais le trimestre.
**Stabilité.** **20 passages** consécutifs du test web sur base neuve (`ent_v3d_web_test`) : **20 verts** ; le test avait déjà passé 20 fois avant la correction (21 passages) : l'intermittence ne se reproduisait pas en local (plan d'exécution favorable) ; la preuve de la cause est le test de base à plans forcés et les cinq tests déterministes ci-dessus, **rouges avant 476, verts après**.
